# Phoenix networking on AWS — design

Status: draft for review · 2026-10-26 · Layer 1 of Phoenix on AWS
Diagram: [`../../architecture/phoenix-networking.png`](../../architecture/phoenix-networking.png)
(source `phoenix-networking.drawio`, generated by `gen_diagram.py`)

## Why

Every Phoenix environment needs a network before anything else can be built:
an address range that never overlaps another, a path to the tooling VPC (where
Backstage's runner reaches every private EKS API), a way out to the internet,
and — for some adopters — a path to their own data centre. Today core-network
assumes a transit gateway estate someone else built by hand, with one
company's regions hardcoded (`dublin`, `frankfurt`, `seoul`, `sao_paulo`).

This design makes the network part of the platform: the first environment in
a region brings that region's network into existence, joined to every region
that already has one, with production and non-production kept apart
everywhere.

## Who it is for

- **The adopter** — an architect who takes this repository for their own
  organisation. They make a handful of platform decisions once (below);
  Backstage applies them from then on.
- **Requesters** — developers, engineers, researchers. They pick a region in
  the environment form and never see networking. If the region has no network
  yet, it is built first, and their request carries on.

## Goals

1. **Hub and spoke, on demand.** One hub region (or two — see Hybrid). Every
   other region gets a transit gateway only when its first environment is
   requested. A new regional transit gateway peers with the hub(s) and with
   every other region that already has one.
2. **Production and non-production never reach each other** by any AWS path:
   directly, across regions, through the tooling VPC, or through central
   egress. On-prem reaches both; whether it passes traffic between them is the
   adopter's edge firewall.
3. **The tooling VPC reaches everything.** Backstage's runner reaches every
   cluster's private API in every region.
4. **Two egress modes, both built:** central (through an egress VPC per region
   in the networking account) and independent (each VPC its own NAT). The
   adopter picks one for the platform.
5. **Three hybrid patterns, all built, all optional:** two IPsec tunnels; one
   Direct Connect with an IPsec VPN as backup; two Direct Connects (which needs
   two hub regions).
6. **Names resolve both ways** with on-prem through Route 53 Resolver.
7. **Workload restrictions live in the clusters**, with Cilium network policy.
   The AWS network lets a segment's VPCs reach each other; Cilium decides what
   pods may actually reach.
8. **Same style as the rest of the repo:** plain Terraform roots, one YAML per
   unit, `modules/context`, one GitHub workflow, `terraform test` with mocks.

## Non-goals

- Creating the networking and tooling accounts (account vending, its own
  design).
- Configuring the on-prem side: edge devices, firewalls, BGP policy beyond
  what AWS needs. The design documents what the on-prem team must set up.
- Traffic inspection. Central egress leaves room for AWS Network Firewall in
  the egress VPC; it is not built now.
- AWS Cloud WAN, IPv6, multiple AWS organisations, PrivateLink service
  sharing.
- Separating teams from each other at the network level (Cilium does that).

## Anti-goals (a failure even if everything applies)

- Any route, in any table, that lets a non-production address reach a
  production one, or the reverse.
- An adopter having to edit Terraform code to choose a mode, a region or an
  address range.
- A requester being asked a networking question.
- Real organisation identifiers (account IDs, OU IDs, company names) anywhere
  in the repository. The old `ipam/` stays local and ignored (see Repository).
- A manual step that is not written down.

## Platform settings (the adopter's decisions)

One file, `phoenix/platform.yaml` in the Backstage repository. Backstage copies
the relevant values into each networking unit's YAML, the way it already
copies account IDs from the account registry. Terraform never reads the
settings file directly.

| Setting | Values | Change later? |
|---|---|---|
| `networking_account_id`, `tooling_account_id` | 12-digit IDs | No |
| `hub_regions` | one region, or two (required for two Direct Connects) | Adding a second hub: yes, with a re-apply of every peering. Removing: no |
| `address_space` | one private supernet; default `10.0.0.0/8` | **No** — fixed at first apply |
| `segment_netmask` | size of each segment's block; default `/10` | No |
| `region_netmask` | size of a segment's block per region; default `/13` (8 regions per segment) | No |
| `vpc_netmask` | per tier; defaults: `sandbox` `/20` (4,096 addresses), `stage` / `uat` / `prod` `/18`; any VPC `/17`–`/22` | Yes (new VPCs) |
| `egress_mode` | `central` or `independent` | Yes, but every VPC is re-applied and loses outbound connectivity briefly — treat as a migration |
| `hybrid` | `none`, `vpn`, `dx_vpn`, `dual_dx`, plus its parameters | Yes |
| `onprem_cidrs` | on-prem ranges (must not overlap `address_space`) | Yes |
| `dns_forwarding` | `{ domain: [on-prem resolver IPs] }` | Yes |
| `share_with` | the organisation, or OUs, the transit gateways and pools are shared with | Yes |

Validation in Backstage and in each module: `address_space` must be RFC 1918,
must not overlap `onprem_cidrs`, and must hold three segments plus a reserve
at `segment_netmask`; `dual_dx` requires two `hub_regions`.

## Topology

### Accounts

| Account | Holds |
|---|---|
| **Networking** | IPAM (delegated admin), every transit gateway and its route tables, peering, central egress VPCs, hybrid connections, the hub DNS VPC with Resolver endpoints |
| **Tooling** | the tooling VPC: Backstage, the `phoenix-mgmt` runner, future tooling |
| **Group accounts** | environment VPCs (core-network), attached to their region's transit gateway |

Transit gateways and IPAM pools are shared with `share_with` through AWS RAM.
Transit gateways have default association and propagation **off**, and
auto-accept shared attachments **on**: every association and propagation is
explicit, and made by Terraform from the networking account.

### Addressing

`address_space` splits into three **segments**, each one summary route
wherever it is used (route tables, on-prem firewalls, Direct Connect allowed
prefixes):

```text
address_space            default 10.0.0.0/8
├── production           1st block at segment_netmask   10.0.0.0/10
├── non-production       2nd                             10.64.0.0/10
├── shared               3rd (tooling VPC, hub DNS VPC, egress VPCs)  10.128.0.0/10
└── reserved             10.192.0.0/10, not provisioned
```

IPAM has a top pool per segment. When a region joins, each segment gets a
**regional pool** of `region_netmask` (the first free block), shared with
`share_with`. A VPC takes `vpc_netmask` from its segment's regional pool, as
core-network already does. Because a region's share of a segment is one
block, a peering needs exactly one static route per segment per region.

With the defaults, a region's /13 holds 32 VPCs at /18 or 128 at /20: in
non-production that is room for well over a hundred sandboxes alongside the
stage and UAT environments. Sandboxes default to /20 because they run small
clusters; pods still take VPC addresses, so 4,096 is enough for a few dozen
nodes. A larger sandbox can ask for more (the platform's catalog, not the
requester, sets the size).

The tier decides the segment: `prod` → production; `sandbox`, `stage`, `uat` →
non-production. The tooling VPC is in shared.

### Transit gateways and route tables

Each transit gateway (hub or regional) has three route tables:

| Attachment | Associated with | Propagates into |
|---|---|---|
| Production VPC | `production` | `production`, `shared` |
| Non-production VPC | `non-production` | `non-production`, `shared` |
| Tooling VPC, hub DNS VPC | `shared` | `production`, `non-production`, `shared` |
| Central egress VPC | `shared` | — (static default routes point at it) |
| On-prem (VPN / Direct Connect gateway) | `shared` | `production`, `non-production`, `shared` (BGP) |
| Peering to another region | `shared` | — (static routes, below) |

And always, in both segment tables:

- `production` has a **blackhole** for the whole non-production segment and
  `non-production` one for the whole production segment. This is what stops
  a packet with a cross-segment destination taking the default route into
  central egress (or a peering) and coming back through `shared`.
- In central mode, `0.0.0.0/0` → that region's egress VPC attachment in
  `production` and `non-production`.

Traffic arriving over a peering or from the egress VPC is looked up in
`shared`, which routes to every local VPC. That is safe because the sending
side's segment table has already decided what may leave: a non-production
table never holds a route to production space, only a blackhole.

### Regions, peering and the hubs

- **Hub region(s):** a transit gateway and its three tables (a `region` unit,
  like any other region), the tooling VPC's attachment (first hub only; made
  by core-network like every VPC's, with `segment: shared`), the hub DNS VPC (when hybrid or
  `dns_forwarding` is set), and the hybrid connection.
- **A new region** gets a transit gateway and three tables, its three regional
  IPAM pools, and in central mode its egress VPC.
- **Peering:** the new region peers with every transit gateway that exists —
  both hubs and every other region (a full mesh; AWS allows 50 peerings per
  transit gateway, enough for this design's scale). Peering does not
  propagate routes, so each peering adds static routes on both sides:

  | Table, on each side | Routes to the other region's |
  |---|---|
  | `production` | production block |
  | `non-production` | non-production block |
  | `shared` | production, non-production and shared blocks |

  Plus, in a region that is not a hub, `production` and `non-production`
  route the shared segment's hub blocks (tooling, hub DNS) and `onprem_cidrs`
  to the **first hub's** peering. With two hubs, losing the first hub's region
  means changing that to the second hub and re-applying (documented runbook;
  automatic failover is not built).

- Regional transit gateways, egress VPCs and peerings are **never removed
  automatically**, even when a region's last environment goes away.

### Egress

| | Central | Independent |
|---|---|---|
| Environment VPC | no NAT gateways; private subnets' default route → transit gateway | NAT gateway(s) in its own public subnets, as core-network does today |
| Egress VPC (per region, networking account, shared segment) | public subnets with NAT gateways (one per AZ), private subnets for the attachment; routes `address_space` back to the transit gateway | not built |
| Segment tables | `0.0.0.0/0` → egress attachment, plus the cross-segment blackholes | no default route |

In both modes an environment keeps its own public subnets and internet gateway
for **inbound** load balancers (istio's external gateway): central egress
governs outbound only.

### Hybrid

| Pattern | AWS side | Hub regions |
|---|---|---|
| `vpn` | customer gateway; one site-to-site VPN connection (two IPsec tunnels, BGP) attached to the hub transit gateway | 1 |
| `dx_vpn` | Direct Connect gateway associated with the hub transit gateway over a transit virtual interface on the adopter's connection; plus a site-to-site VPN as backup (BGP prefers Direct Connect: AWS prefers it for equal prefixes) | 1 |
| `dual_dx` | one Direct Connect gateway; two connections (one near each hub) with a transit virtual interface each; the gateway associated with **both** hub transit gateways | 2 |

- The Direct Connect connections themselves are ordered by the adopter; the
  design takes their IDs as parameters and creates the virtual interfaces,
  gateway and associations.
- Allowed prefixes on a Direct Connect gateway association: the three segment
  blocks (summaries), so on-prem learns production, non-production and shared.
- On-prem attachments sit in `shared`, so on-prem reaches both segments, and
  both segments reach on-prem. Who on-prem may talk to which segment is the
  adopter's edge firewall and their own network design — documented, not
  enforced here.
- Outputs for the on-prem team: tunnel endpoints and inside addresses, BGP
  ASNs, the prefixes AWS advertises, and the prefixes it expects.

### DNS

- **Hub DNS VPC** (networking account, shared segment, each hub region): Route
  53 Resolver **inbound** endpoint (on-prem forwards AWS zones to it) and
  **outbound** endpoint with one forwarding rule per `dns_forwarding` domain.
- The rules are shared through RAM; core-network associates every shared rule
  with each VPC it creates.
- Each environment's **internal** private zone (infrastructure's `dns` unit) is
  associated with the hub DNS VPC(s) — cross-account authorisation, then
  association — so on-prem resolves environment names through the inbound
  endpoint.

### Cilium

A new `k8s-installs` component, `cilium`, in every cluster's baseline. My call
on how it sits:

- **Chaining mode with the AWS VPC CNI** (`cni.chainingMode: aws-cni`,
  native routing, no masquerade, kube-proxy kept): pods keep VPC addresses,
  so IPAM planning and the routing above are unchanged. Cilium only enforces
  policy.
- **Default cluster-wide egress policy** (installed with it), allowing:
  the cluster's own VPC CIDR; the tooling VPC; DNS (kube-dns, the VPC
  resolver); EKS Pod Identity and instance metadata (`169.254.170.23`,
  `169.254.169.254`); and the internet (everything outside RFC 1918).
  Everything else private — other environments, the other segment (already
  blocked by AWS), on-prem — is denied unless a policy opens it.
- **Opening more:** `spec.egress_allow` on the cilium unit (CIDRs and FQDNs,
  platform-managed), and namespaced `CiliumNetworkPolicy` objects teams ship
  with their apps through Argo CD (FQDN rules such as `*.corp.local` use
  Cilium's DNS proxy).
- Catalog: `component-cilium` with no prerequisites; every other component
  depends on it being present only through the baseline order (installed
  right after cluster-config).

## Units (the `networking/` layer)

New top-level folder, same conventions as `infrastructure/`:

```text
networking/modules/<unit>/                 plain Terraform roots (+ context)
networking/environments/<scope>/<unit>[.<instance>].yaml   written by Backstage
```

| Unit | Scope | Instance | Creates |
|---|---|---|---|
| `ipam` | `global` | — | IPAM (operating regions = every region that has joined), segment pools, one regional pool per segment per region, RAM shares |
| `region` | `<region>` | — | transit gateway, three route tables, blackholes, RAM share; central mode: egress VPC, its attachment, default routes |
| `peering` | `<region>` | `<peer region>` | peering attachment (requested from `<region>`, accepted in the peer), static routes on both sides; two providers from the YAML |
| `hub` | `<hub region>` | — | hub DNS VPC with Resolver endpoints and rules; RAM shares of the rules |
| `hybrid` | first hub region | — | per `hybrid`: customer gateway + VPN, and/or Direct Connect gateway, transit virtual interfaces, associations; with `dual_dx`, a second provider for the second hub (from the YAML) |

Units use `modules/context` with `group: platform`, `environment: network`,
`tier: prod` (my call: names come out as `platform-network-<region code>-…`,
and tags mark it long-lived). State keys follow context:
`platform-network/<scope>/<unit>[.<instance>]/terraform.tfstate`.

The workflow gains the `networking` project (path check, state key with an
instance, GitHub-hosted runners: AWS APIs only).

## How a request flows

1. A requester asks for an environment in `<region>`.
2. Backstage checks its catalog for a `phoenix-region` entity for `<region>`.
   If there is none, it writes, in order:
   1. `ipam.yaml` with `<region>` added to `regions` (an edit, not a new file);
   2. `<region>/region.yaml`;
   3. `<region>/peering.<peer>.yaml` for every region that already has one
      (hubs included);
   4. the `phoenix-region` entity for `<region>` (in Backstage's own catalog,
      `phoenix/regions/<region>.yaml`, like cluster entities).
3. Then the environment's own units, as today: core-network → core-platform →
   … The orchestrator runs networking units first and stops the chain if one
   fails.

First-time setup (once, by the adopter, documented): delegate IPAM
administration to the networking account and enable RAM sharing with the
organisation (from the management account); then apply `ipam`, the hub
`region`, `hub`, and `hybrid` if chosen; then the tooling VPC (a core-network
unit in the tooling account, segment `shared`).

## Testing

As every other module: `terraform test` with mock providers, no AWS. At
least:

- **Reachability matrix** (on `region` + `peering`, from planned tables): a
  production VPC's table has no route into non-production space, holds the
  blackhole, and (central) its default route goes to egress; the same the
  other way; `shared` reaches all three.
- Peering adds exactly the static routes above, on both sides.
- IPAM: adding a region creates three regional pools of `region_netmask`;
  `address_space` overlapping `onprem_cidrs` fails the plan.
- Hybrid: each pattern plans only its own resources; `dual_dx` with one hub
  fails.
- core-network: segment from tier; central mode has no NAT gateways and a
  default route to the transit gateway; independent mode is unchanged.
- cilium: chaining values; the default policy's allowed destinations.

The real proof needs an AWS organisation (part 15 of the series): attach two
VPCs per segment in two regions and test reachability both ways.
